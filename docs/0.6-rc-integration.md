# OpenUsage Bar 0.6 RC 集成候选

本文记录 0.6 RC 的本地集成事实。它不是发布公告，也不代表公开 Canary
已经开始。

## 集成范围

候选分支 `integration/0.6-rc` 以 release hardening 为基础，统一装配了此前
独立审查的功能切片：

- Codex 本地 Token 历史与订阅额度对账；
- MiniMax 中国站、国际站的数据源隔离；
- Cursor 剩余额度语义；
- Kiro / CodeWhisperer 订阅额度语义；
- OpenAI Organization cache、input、output 与 total 用量；
- Claude Code、OpenCode 等本地客户端覆盖检查；
- GLM、Kimi、Qwen 等 Provider 的权威来源审计；
- Moonshot / Kimi 官方余额接入；
- Provider Adapter Kit；
- Supported Billing/Cost 与 `api_spend` source fact 的目录一致性约束；
- Local API v1 N-1 兼容策略；
- PR CI 与 Pre-release 的依赖审计及隔离安装/升级/回滚门禁对齐；
- 无遥测 Canary 入口，包含脱敏 Balance 与能力证据聚合；
- 无遥测 Canary 跨界面校验器，自动对齐已安装 CLI 与 Local API，并保留
  菜单栏可见性人工门禁；
- 常驻进程性能预算；
- 仅供性能测量工具使用的匿名 source-class 刷新计时。
- 后台 Provider 刷新的有界只读 Keychain 访问，以及仅允许 Step Plan
  Session 写入的私有 stdin helper。

对应的独立审查记录为 Draft PR #35 至 #47；release hardening 基线为
PR #15。集成 PR 是唯一的 0.6 RC 共存候选，独立 PR 继续保留为设计与
审查证据，不应被逐个当作完整产品候选发布。

## 集成时发现并修复的问题

Moonshot 余额接入为 `/v1/snapshot` 新增 `balances`。Local API v1 兼容
策略规定 additive 字段不得在同一 major 版本中变为必填，因此当前 Schema
保留 `balances` 的类型约束，但不要求旧 snapshot 必须包含该字段。

验证同时覆盖：

- 当前校验器读取冻结的 0.4.2 N-1 snapshot；
- 当前校验器读取带未知 additive 字段和 `balances` 的 snapshot；
- 当前 Server 输出仍包含 `balances`；
- 未知字段不能绕过凭证与隐私字段检查。

后台刷新另发现 Step Plan Adapter 绕过了共享的有界 Keychain Reader，
直接调用原生 Security API。在新的本地签名尚未获得 Keychain 授权时，
调用会无限等待系统交互，进而拖住整轮刷新。当前修复让所有后台读取统一
经过 5 秒可终止、可回收的只读边界；私有 helper 不提供任何读取能力，只
接受固定的 Step Plan `Oasis-Token` 写入，密钥仅通过 stdin 传递，不进入
argv、日志或响应。任意账号写入、读取请求和畸形 JSON 均 fail closed。

实机继续验证时确认，ad-hoc 本地签名每次重建都会改变 CDHash；新签名尚未
获得钥匙串 ACL 授权时，5 秒后台边界只能安全失败，不能替用户完成系统级
授权。当前候选因此在“高级与修复”增加显式前台修复入口：只使用固定
`/usr/bin/security`、固定应用 service 和已配置账号，单项最长等待 90 秒；
凭证 stdout/stderr 均直接丢弃，界面只返回已授权、未找到和未允许的数量。
Kiro 只检查其既有只读 service，不刷新、改写或输出登录信息。后台刷新仍
保持 5 秒 fail closed；macOS 的持久授权必须由用户在系统提示中亲自确认。

首次事务安装该修复包时又发现：安装器只清理 Activity helper，已打开的
Provider Settings 仍保留旧进程镜像，导致磁盘已更新但修复窗口继续运行旧
代码。当前安装生命周期已把两个可见 helper 都纳入精确路径、启动时间和
bundle id 保护的停止/回滚/恢复流程；同一 Settings 可执行文件带 `daemon`
参数的 collector 不匹配该规则，不会被误杀。

集成候选运行一段时间后，Cursor direct enrichment 在 40 秒边界附近出现
可复现的 Last-good 保留与超时退避；独立脱敏只读探测在同机取得可用剩余
额度，但 wall time 为 `38.41s`，仅剩 1.59 秒余量。50 秒候选进入完整
Provider 刷新后仍在 `52.46s` 被有界回收；60 秒候选的冷启动后台刷新又在
`60.036s` 到达边界，而紧接着的安装包前台全量刷新在 `62.90s` 完成并把
Cursor 恢复为实时 `ok`。因此最终回归测试锁定至少 75 秒的 direct 边界，
并把完整交互刷新硬上限从 120 秒同步提升到 160 秒；它仍覆盖
`auto 12s + direct 75s + daily 60s + 5s` 的回收余量。失败、空结果、
Backoff 和 Last-good 选择语义均未改变。进一步追踪确认耗时来自 OpenUsage
同时轮询所有 Provider，而 Cursor 自身的上游请求有 10 秒内部边界。独立
OpenUsage 工作树提交 `c63a47c` 新增可选的
`export --source direct --provider cursor` 精确采集；相关 Go 包测试通过，
本机只读结果由 75 秒以上超时降为 `3.60s`，只返回 1 条 Cursor `OK`
快照。OpenUsage Bar 会用 3 秒无凭证 help 探测该能力，支持时使用 15 秒
精确边界，不支持时仍走上述 75 秒兼容 fallback；两条路径都不解析 UI、
不输出凭证，也不把失败写成零。最终安装包的完整 `--fresh` 实测为
`7.63s`，同轮 Local API 中 Cursor 与 Kiro 均为实时 `ok`；Step Plan 保留
`invalid_response` 与 Last-good，没有被误写成零或伪成功。

同一自定义构建最初被 Data Health 的精确 revision 门禁显示为“不支持此
OpenUsage 版本 / 0/35 Provider”。修复没有接受任意开发版本，而是只允许
独立审计过的 `c63a47c`，并同时要求 `0.23.0` 基线、git describe revision
自洽以及运行态 35 个 Provider 与规范目录完全一致。真实二进制探测现返回
35/35；未知开发 revision、版本漂移和 Provider 集合漂移仍 fail closed。
候选重新安装后，真实 `activity.sqlite3` 的兼容性健康记录已通过同一发现
逻辑更新；原生 Data Health 页面最终显示 `Ok / 兼容 / 已检测 35 / 35`。

随后真实 Step Plan 刷新暴露出诊断歧义：钥匙串、网络与响应解析失败原先
都会写成 `invalid_response`。当前实现将它们分别标为
`keychain_unavailable`、`network_error` 与 `invalid_response`，Provider
Center 也会把钥匙串失败升级为需要处理的连接问题，并使用“当前额度”而
不是原始 source id 作为标题。最终修复包确认两个 Helper 与构建产物的
SHA-256 一致后，新的常驻采集记录 Step Plan
`keychain_unavailable` 且 Last-good 仍保留；同轮 Kiro 官方额度继续实时
`ok`，因此没有把 Kiro 的正常连接误判为需要重配。原生 Provider Center
实测将 StepFun Step Plan 排到最前并显示“需要处理 / 当前额度需要有效连接”，
没有代替用户接受系统 Keychain ACL 提示。实机还暴露了配置账号
`step-plan-main` 与 OpenUsage 自动发现实例同名时的 family 冲突；Provider
Center 现在让已配置连接优先拥有该 Provider ID，连接问题会落到可编辑的
StepFun Step Plan，而不会挂到旁边的只读自动发现项。
