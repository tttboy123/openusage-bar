# OpenUsage Bar 0.6 RC 集成候选

本文记录 0.6 RC 的本地集成事实。它不是发布公告，也不代表公开 Canary
已经开始。

## 集成范围

候选分支 `integration/0.6-rc` 以 release hardening 为基础，统一装配了此前
独立审查的功能切片：

- Codex 本地 Token 历史与订阅额度对账；
- MiniMax 中国站、国际站的数据源隔离；
- Cursor 剩余额度语义；
- Kiro / CodeWhisperer 订阅额度语义；
- OpenAI Organization cache、input、output 与 total 用量；
- Claude Code、OpenCode 等本地客户端覆盖检查；
- GLM、Kimi、Qwen 等 Provider 的权威来源审计；
- Moonshot / Kimi 官方余额接入；
- Provider Adapter Kit；
- Supported Billing/Cost 与 `api_spend` source fact 的目录一致性约束；
- Local API v1 N-1 兼容策略；
- PR CI 与 Pre-release 的依赖审计及隔离安装/升级/回滚门禁对齐；
- 无遥测 Canary 入口，包含脱敏 Balance 与能力证据聚合；
- 无遥测 Canary 跨界面校验器，自动对齐已安装 CLI 与 Local API，并保留
  菜单栏可见性人工门禁；
- 常驻进程性能预算；
- 仅供性能测量工具使用的匿名 source-class 刷新计时。
- 后台 Provider 刷新的有界只读 Keychain 访问，以及仅允许 Step Plan
  Session 写入的私有 stdin helper。

对应的独立审查记录为 Draft PR #35 至 #47；release hardening 基线为
PR #15。集成 PR 是唯一的 0.6 RC 共存候选，独立 PR 继续保留为设计与
审查证据，不应被逐个当作完整产品候选发布。

## 集成时发现并修复的问题

Moonshot 余额接入为 `/v1/snapshot` 新增 `balances`。Local API v1 兼容
策略规定 additive 字段不得在同一 major 版本中变为必填，因此当前 Schema
保留 `balances` 的类型约束，但不要求旧 snapshot 必须包含该字段。

验证同时覆盖：

- 当前校验器读取冻结的 0.4.2 N-1 snapshot；
- 当前校验器读取带未知 additive 字段和 `balances` 的 snapshot；
- 当前 Server 输出仍包含 `balances`；
- 未知字段不能绕过凭证与隐私字段检查。

后台刷新另发现 Step Plan Adapter 绕过了共享的有界 Keychain Reader，
直接调用原生 Security API。在新的本地签名尚未获得 Keychain 授权时，
调用会无限等待系统交互，进而拖住整轮刷新。当前修复让所有后台读取统一
经过 5 秒可终止、可回收的只读边界；私有 helper 不提供任何读取能力，只
接受固定的 Step Plan `Oasis-Token` 写入，密钥仅通过 stdin 传递，不进入
argv、日志或响应。任意账号写入、读取请求和畸形 JSON 均 fail closed。

  使用同一版本身份；
- Python：870 项通过；release 构建脚本已重复执行覆盖率与发布构建门禁；
- Swift：255 项、21 个 Suite 通过；
- Provider catalog、Local API Schema 与 Swift 生成文件无漂移；
- release secret tree scan：0 项；
- privacy scan：0 项；
- App、Activity helper、Provider Settings helper 均完成本地签名与包结构校验；
- `dist/OpenUsage Bar.app` 构建成功，并已事务式安装为
  `/Applications/OpenUsage Bar.app` 的本地候选；回滚备份保留；
- Provider Adapter Kit 在全新 detached worktree 中按公开文档直接通过
  14-case Conformance，随后 clean-checkout build 通过；
- 没有写入或回显用户 Keychain，也没有变更 Provider 配置；当前候选的新
  本地签名尚未获得 Step Plan / MiniMax Keychain 读取授权，因此这些来源
  如实保持 `auth_required` 与 Last-good，而不是阻塞其他 Provider。

版本身份审计首先从提交 `e3dcf45` 的 CI 制品发现：集成分支虽然名为
`0.6 RC`，产物仍自报 `0.4.4 (8)`，因此不能作为可区分的外部 Canary
候选。当前修复使用 RED → GREEN 的 Bundle 契约升级到 `0.6.0 (9)`；本地
重建后 ZIP、DMG checksum、release artifact audit、SPDX SBOM、隐私扫描及
隔离 clean install / upgrade / rollback / uninstall 全部通过。未提交工作树
生成的本地包只用于验证，不发布；可分发候选必须由提交后的远端 CI 重新生成。

随后使用远端 `0.6.0 (9)` artifact 的诊断入口读取当时仍在运行的
`0.4.4 (8)` Local API v1。旧 API 的 capability sources 尚未包含新增的五个
证据字段，初次导出按预期暴露兼容缺口；修复后，完整缺失的旧证据组被保守
表示为 `unknown` / `unverified` 和空 factFamilies，部分缺失仍拒绝。真实
运行态的诊断 v1 与七日范围 v2 均导出成功，文件权限为 `0600`，隐私扫描
均为 0；没有输出或记录个人 Token 数值、Provider 身份或账号引用，也没有
替换当时的安装。

发行 ZIP 的诊断入口另做了解压后隔离验证。`privacy_scan.py` 现在随包
携带纯数据的规范 `activity_schema.py`，不依赖源码仓库或已安装 Python
包；它仍按完整表集合与精确列签名校验 SQLite，未放宽隐私边界。回归测试
在清空 `PYTHONPATH` 的隔离目录中扫描真实规范账本，防止再次出现仅在源码
目录可运行的发行缺陷。

性能测量工具现在可以在显式测量时按 `network`、`local_file` 和
`child_process` 聚合单调时钟耗时及
success/backoff/timeout/unavailable/failed 结果。报告不保留 Provider、
source ID、账号、端点、路径、原始 Payload、Prompt 或 Response，也不通过
Local API v1 或诊断包公开。旧版应用和未启用插桩的刷新继续明确返回
`not_observable`。

提交 `b34bd70` 的 Draft PR #48 CI 在 8 分 48 秒内完成：锁定依赖审计、
完整 Git 历史凭证扫描、Python/Swift 构建与测试、开发签名打包、ZIP/DMG
制品审计、隔离安装/升级/四类故障回滚/卸载以及 artifact 上传均通过。随后
下载该次 CI 的 `0.6.0 (9)` ZIP 和 DMG 再做独立审计，并直接从 ZIP 解包的
Collector 在隔离 HOME 中生成 `0600` 权限的 source-class 报告；没有安装到
`/Applications`，报告与终端也没有输出 Provider 身份、Token、账号或原始
数据。

安全收窄后的本地安装候选随后完成三轮真实全量刷新：中位数
`51.493s`、p95 `52.044s`，0 超时、0 失败；常驻 CPU p95 `0.001%`、
唤醒 p95 `2.200/s`、常驻物理占用峰值 `50.4 MiB`、Activity 峰值
`97.8 MiB`。network、local_file、child_process 的单次最大耗时分别为
`10.048s`、`0.150s`、`38.133s`。六项预算全部通过，公开报告不含本地

`docs/performance-baselines/0.6.0-build9-2026-07-30.json`。

随后按 Canary 的跨界面一致性步骤复核发行入口，发现 collector parser 与
Local API 已支持 `snapshot`，但冻结设置 Helper 的严格命令白名单遗漏了它，
导致已安装 App 的文档命令无输出并返回 2。修复先以真实入口测试产生 RED，
再把只读 `snapshot` 加入白名单；没有放开未知命令或任何 mutation。重建并
事务安装后，`API → CLI → API` 三次读取均为同一 `dataRevision=47027`，
移除唯一允许不同的非语义 `generatedAt` 后完整 JSON 相等。当前 App 深度
签名、本地 API 与两个 LaunchAgent 均正常。

在此基础上新增随发行 ZIP 分发的 `verify_canary_surfaces.py`。它先以固定
的系统 `codesign --verify --deep --strict` 验证安装包，再按
`API → CLI → API` 顺序读取；遇到后台刷新导致的 revision 漂移会整轮有界
重试。同一 revision 下只排除顶层 `generatedAt` 和 capacity 行中由查询时钟
重新计算的 `freshnessSeconds`，其他事实差异一律 fail closed。实机进一步
证明此前“只排除 generatedAt”的手工规则不完整：`dataRevision=47078`
一致时，CLI 与 API 仍可能因跨秒查询出现 1 秒 freshness 差异。当前规则
没有忽略状态、质量、stale、重置或任何用量事实。发行目录中的独立脚本在
清空 `PYTHONPATH` 后对已安装 `0.6.0 (9)` 返回
`dataRevision=47095`、`apiCliSnapshot=pass`、
`sourceHealthAgreement=pass`、`visualMenu=pending_manual`；输出文件权限
`0600`，隐私扫描为 0。菜单栏图标及弹窗仍必须由测试者目视确认，进程和
脚本结果不能代替该证据。

Kiro 的 OpenUsage 本地 Token 活动也完成了独立的真实账号验收。一个有界
30 日离线探测只判断是否存在按日模型行，不打印或保存 Token 数值、路径、
账号身份、Prompt、Response 或原始 JSON；结果为非空。因此目录中
`kiro_cli` 的 `openusage` 来源只把 `detection` 与 `token_activity` 的
验证等级从 `fixture` 提升为 `live_account`。这不改变独立的
`kiro_codewhisperer_api` 官方订阅额度事实，也不把两类事实相加。完整重建
并事务安装后，已安装 App 的 `/v1/capabilities` 返回相同来源、事实族与
验证等级；App 深度签名和 Local API 健康检查通过。重新生成的 ZIP、DMG、
manifest 与 SPDX SBOM 通过 artifact、DMG、隐私和隔离
install / upgrade / rollback / uninstall 烟雾门禁。
